# Architecture & Security Decisions

Each decision: what we chose, the alternatives, why, and when we would choose differently.
Status labels: **deployed** (runs in CI / locally), **designed** (written + statically validated, not applied to AWS).

---

## D1. Weather data source: Open-Meteo, collected by a CronJob
- **Chosen:** Open-Meteo API, called every 15 min by a Kubernetes CronJob; one batched request for all cities.
- **Alternatives:** OpenWeatherMap / WeatherAPI (need an API key); fetching on each user request.
- **Why:** no API key means **no third-party secret to store, rotate or leak**. A separate collector decouples user traffic from the external API (no rate-limit risk from page views, and the UI still works if the API is down; it shows the latest stored data).
- **Trade-off:** Open-Meteo's free tier is for **non-commercial use**. A real product needs their paid plan or another provider, and then the key goes into a secret manager (Secrets Manager + External Secrets Operator).
- **At scale:** a paid provider with an SLA; a queue between collector and DB if many cities or high frequency.

## D2. App stack: FastAPI backend, static frontend on nginx, PostgreSQL
- **Chosen:** Python/FastAPI (read-only API), plain HTML/JS on `nginx-unprivileged`, PostgreSQL.
- **Alternatives:** Go (smaller image, more code); a React SPA (large npm supply chain); DynamoDB (native IAM, weak at time-range queries).
- **Why:** smallest amount of code that is easy for a junior to read; very few dependencies (small attack surface). Postgres handles both "latest per city" and "history by time range" through one primary-key index.
- **Security details:** all SQL parameterized; external API data validated before storage; frontend writes data only with `textContent` + strict CSP (no XSS); `/docs` disabled; DB errors return a generic 503 (no internal details leak).

## D3. One public entry point
- **Chosen:** only the frontend (nginx) is exposed. It proxies `GET /api/*` to the backend. The backend Service is internal (ClusterIP).
- **Why:** `/metrics`, `/readyz` and everything else on the backend are unreachable from the internet. Defense in depth: NetworkPolicies also allow backend ingress only from the frontend and Prometheus.

## D4. No long-lived credentials anywhere
| Who | Gets access to | How |
|---|---|---|
| GitHub Actions | AWS | OIDC, trust pinned to `repo:<owner>/<name>:environment:<env>` |
| GitHub Actions | GHCR, image signing | the job's short-lived `GITHUB_TOKEN` + Sigstore keyless signing |
| Pods (AWS) | AWS APIs / RDS | EKS Pod Identity, one IAM role per workload; RDS IAM auth tokens (15 min) |
| Pods (local) | Postgres | per-workload passwords generated by Terraform into K8s Secrets (never in git) |
| RDS master user | admin bootstrap only | generated + rotated (30 days) by AWS in Secrets Manager |

## D5. Least privilege in the database
- Three DB users: `weather_api` (SELECT only), `weather_collector` (SELECT/INSERT/DELETE), `weather_migrate` (owns the schema).
- Each workload has its own ServiceAccount → its own IAM role → may log in only as its own user.
- A compromised API pod cannot write or delete data.
- **Why the collector has DELETE:** it also runs the retention cleanup (rows older than `RETENTION_DAYS`, default 90) in the same transaction as the insert, so there is no second job with its own credentials. **Risk:** a compromised collector could delete history. **Limits on that risk:** the collector has no ingress, its egress is limited to HTTPS (no private ranges, no metadata service) plus Postgres, and it is a short scheduled Job (every 15 min), not a long-running service. **Recovery:** locally there is **no** backup or point-in-time recovery: the CloudNativePG cluster has no backup to object storage, and replicas don't help because a delete replicates to them immediately. Automated backups and PITR exist only in the AWS RDS design (`backup_retention_period = 7` in `rds.tf`), which has not been applied. **Stricter option:** a separate retention CronJob with its own DELETE-only role, or time-partitioned tables where the migrate role drops old partitions, leaving the collector with INSERT only.

## D6. Kubernetes hardening
- Pod Security Admission **restricted** enforced on the app namespace: non-root, no privilege escalation, all capabilities dropped, seccomp RuntimeDefault, read-only root filesystem.
- **Default-deny NetworkPolicies**, then one explicit allow per flow. The collector may reach the internet on 443 but **not** private ranges or the cloud metadata service.
- `automountServiceAccountToken: false`: no workload talks to the Kubernetes API.
- Resilience: 2+ replicas, topology spread across nodes/zones (on kind the "zones" are only node labels: this tests the scheduling rules, not real AZ failure), PodDisruptionBudgets, HPA, rolling updates with `maxUnavailable: 0`, liveness (process only) vs readiness (DB reachable) probes.
- Schema migration runs as a Helm pre-upgrade hook; a failed migration fails the release and the old version keeps serving (`atomic`).

## D7. Infrastructure targets: local/CI (deployed) and AWS (designed)
- **Chosen:** one Helm chart, two environments.
  - `infra/local`: Terraform builds a kind cluster, CloudNativePG (3-instance Postgres with automatic failover), Prometheus/Grafana, metrics-server, and the app. Used on a laptop and in CI.
  - `infra/terraform`: the AWS production design (VPC, EKS, RDS, ECR, WAF, OIDC, Pod Identity). Validated, Checkov-scanned and unit-tested with a mocked provider, but **not applied**.
- **No ingress-nginx:** retirement was announced in November 2025 (maintenance ended March 2026), so we don't put an unmaintained component on the public path. Local uses a NodePort mapped to `127.0.0.1`; AWS uses the ALB (Load Balancer Controller) + WAF.

## D8. AWS network & cluster
- 3 AZs; public subnets hold only ALB/NAT; nodes in private subnets; RDS in isolated DB subnets with no internet route. VPC flow logs on.
- **EKS API endpoint:** public **but restricted by CIDR** and IAM, so GitHub-hosted runners can deploy. `prod_guardrails` forbids `0.0.0.0/0` in prod. **At scale:** private-only endpoint + self-hosted runners inside the VPC (or a pull-based GitOps tool like Argo CD, so CI needs no cluster access).
- **Node IMDSv2 with hop limit 1:** ordinary pods (on the pod network) can't get the node role's credentials. The IMDS token reply is limited to one network hop, and a pod sits one hop further away. Pods get their own credentials from Pod Identity instead.
  - **It is a layer, not a boundary.** It does **not** stop:
    - pods with `hostNetwork: true`, which share the node's network, so the reply reaches them;
    - anything with node-level access: a privileged or `hostPath` pod, a container escape, SSM/SSH on the node.
    
    Some system add-ons legitimately run with hostNetwork (VPC CNI, kube-proxy, the Pod Identity agent), so they could read the node role.
  - **What actually blocks those paths:**
    - Pod Security **restricted** in app namespaces forbids hostNetwork, privileged, hostPath and running as root (the smoke test proves a privileged pod is rejected);
    - default-deny egress NetworkPolicies (the collector's internet rule explicitly excludes `169.254.169.254`);
    - keeping the node role to the EKS managed node policies (worker, ECR pull, CNI) so a stolen node role is worth little;
    - limiting who may create pods in `kube-system`.
- CI deploy role: `AmazonEKSEditPolicy` scoped to the `weather` namespace only (cannot touch `kube-system` or RBAC).
- WAF: per-IP rate limit + AWS managed rules (IP reputation, common attacks, known bad inputs incl. Log4Shell).

## D9. Cost vs. resilience switches (AWS)
Dev defaults are cheap; `prod.tfvars.example` flips them, and the `prod_guardrails` validation **rejects** a prod config that is weaker:

| Setting | dev | prod |
|---|---|---|
| NAT gateways | 1 | 1 per AZ |
| RDS | single-AZ | Multi-AZ |
| Nodes (min) | 2 | 3 |
| Log retention | 30 days | 365 days |

## D10. Checkov findings policy
Real issues are fixed (RDS secret rotation, exact module pins, state-bucket lifecycle). The remaining checks are skipped **with a written reason** in `infra/.checkov.yaml` or inline `checkov:skip` comments. Categories:
- **False positives:** the setting exists but Checkov can't see it inside a community module (EKS secrets encryption, RDS backups, default SG, secret rotation).
- **Variable-controlled:** log retention, EKS endpoint CIDRs.
- **Accepted with reason:** EKS public endpoint for GitHub-hosted runners; AWS-published LB-controller IAM policy; registry modules pinned by exact version + lock file instead of git commit hashes.

**The three IAM checks (CKV_AWS_109, CKV_AWS_111, CKV_AWS_356): scoped exception, not a global skip**
- **What the checks mean:**
  - 109: permissions-management actions without resource limits;
  - 111: write actions without resource limits;
  - 356: `"Resource": "*"`.
- **Where they fire:** without any exception, Checkov 3.4.11 reports 17 findings. All 17 are policy documents inside the pinned `terraform-aws-modules/eks-pod-identity` 2.11.0 call `lb_controller_pod_identity` in `eks.tf`.
  - Only one of those documents is attached: the **AWS-published Load Balancer Controller policy**. The others (appmesh, ebs_csi, velero...) are templates the module builds but doesn't use (`count = 0`).
  - That policy creates ALBs, target groups and security groups whose ARNs don't exist yet, so `"*"` can't be narrowed up front. AWS limits its modify/delete actions with `elbv2.k8s.aws/cluster` tag conditions.
  - Only the controller's ServiceAccount can use it, through Pod Identity.
- **How the exception is scoped:** `checkov:skip` comments **inside that one module block**. Checkov applies them only to resources of that module instance. Nothing is skipped in `.checkov.yaml`.
- **Verified** with Checkov 3.4.11 in Docker, using the repo config:
  - adding an over-broad policy (`iam:*`, `ec2:*` on `"*"`) to our own code → **5 failures** (CKV_AWS_107, 109, 110, 111, 356);
  - removing it → **0 failed**.

  Command to repeat it: add a `data "aws_iam_policy_document"` with `resources = ["*"]` in `infra/terraform`, then `docker run --rm -v "$PWD/infra:/infra" -w /infra bridgecrew/checkov:3.4.11 -d . --config-file .checkov.yaml --quiet --compact`.
- **Remaining limits:**
  - The exception covers the whole module instance, all 22 of its policy documents, not just the 17 findings. A future module version could change those policies without a new finding. The version is pinned, so that only happens through a reviewed version bump (Dependabot PR), and IAM diffs in such a bump need a human look.
  - Narrower option: a Checkov **baseline** file per finding. It was rejected because it keys on the downloaded module's file path, which includes a git hash, so it breaks on every refresh.
  - Stricter option: our own copy of the LB Controller policy with tag conditions on every write action.

**EKS public API endpoint (CKV_AWS_38/39):** see D8.

## D11. Supply chain
- Python deps pinned; `pip-audit` in CI (it already caught Starlette CVEs in the first pins).
- Terraform modules pinned to exact versions; provider hashes in `.terraform.lock.hcl`.
- Container images: immutable tags (ECR), signed (cosign keyless) and verified before deploy; RDS CA bundle downloaded with a pinned SHA-256 checksum.
- kind node image pinned by digest.

## D12. Public demo exposure
- **What is exposed:** the Demo workflow publishes two Cloudflare quick-tunnel URLs, one for the app and one for Grafana.
- **Who can see the URLs:** they appear in the run annotations and the step summary. The repo is public, so **anyone can read the URLs** while the demo is up. The approval to start a run (whoever can press "Run workflow") is separate: it does **not** control who opens the URLs afterwards.
- **What a visitor gets:**
  - App: the same read-only UI that is meant to be public anyway.
  - Grafana: anonymous **Viewer**, with only the 4 Weather dashboards loaded and no admin password printed anywhere. However, a Viewer can still send **any** PromQL query to the Prometheus data source through Grafana's query API. In practice anyone can read every metric of that throwaway cluster: pod names, resource usage, request rates. None of it is a secret, and nothing user-related is stored, but it is more than "4 dashboards".
- **Limits:** 1–120 minutes; the job's hard timeout is 150 minutes; runner, cluster and tunnels are destroyed when the job ends; a new demo cancels the running one.
- **Recommendation:** keep it as an **explicitly time-limited demo**: short runs (30 min), started only when someone is about to look, and stopped after.

| Option | Effect | Cost |
|---|---|---|
| Keep it as is (chosen) | anyone who reads the log can open the URLs during the run | none |
| Grafana "public dashboards" (shared dashboard links) instead of anonymous access | visitors run only the queries saved in those panels | small config change; preview-level feature, check per Grafana version |
| Mask the URLs in the log and send them some other way (e.g. an encrypted artifact) | URLs are not public | needs a delivery channel |
| Make the repo private | logs visible to collaborators only | reviewers need access; changes the submission |
| Cloudflare Access / named tunnel with login | real authentication | a Cloudflare account and an API token stored as a secret |

Changing repo visibility, access controls or a running demo is the owner's decision. None of these is applied by default.

## D13. Image signatures: verified in CI, not enforced in the cluster
- **Today:** the deploy step runs `cosign verify` on the exact digest, against this repo's `ci.yml` identity on `main`, before Helm gets the image. A tampered or unsigned image therefore never reaches the deploy. GHCR tags are only `sha-<commit>`.
- **Gap:** the cluster itself does not check. Someone with cluster write access could run `kubectl set image` with an unsigned image and it would run.
- **Why not now:** an admission controller (Sigstore policy-controller or Kyverno `verifyImages`) is one more always-on component with its own failure mode: if it fails closed, no pod can start. On a throwaway kind cluster, where CI is the only deployer, it would add nothing. On AWS it is **the next step**, together with ECR immutable tags (already on in the design).
